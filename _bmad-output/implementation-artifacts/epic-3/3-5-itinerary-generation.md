# Story 3.5: Proposal Agent — Itinerary Generation

Status: done

## Story

As a travel agent,
I want the system to generate a day-by-day itinerary grounded in verified venue data,
so that my client receives a specific, actionable trip plan they can follow.

**Depends on:** Story 1.3 (LangGraph Orchestrator — `AdvisoryState`, `LLMServiceProtocol`, `VectorStoreProtocol`), Story 1.4 (Profiling Agent — completed `TravelerProfile`), Story 2.1 (Qdrant Vector Store — `QdrantVectorStore` implementing `VectorStoreProtocol`), Story 2.3 (Hybrid Search — `HybridSearchService`), Story 2.4 (Freshness Tracking — `evaluate_freshness`, `filter_with_warnings`), Stories 3.1-3.4 (Calculation Agent — `AdvisoryState.calculations` with budget allocation, accommodation matches, routing, insurance)

**FRs implemented:** FR-10 (Day-by-Day Itinerary Generation)
**NFRs enforced:** NFR-1 (Zero Hallucination — every entity traced to Vector Store)

### AC-2: Day-by-Day Itinerary Structure

**Given** a completed Traveler Profile and Calculation results in `AdvisoryState`
**When** the Proposal Agent runs via `agents/proposal/agent.py`
**Then** a day-by-day itinerary is generated with one `ItineraryDay` per trip day
**And** each `ItineraryDay` contains time blocks for morning, afternoon, and evening
**And** each time block contains an `ActivitySlot` with: venue name, venue entity ID, activity description, estimated duration, and estimated cost

### AC-3: Entity Traceability — Zero Hallucination

**Given** the Proposal Agent generates an itinerary
**When** venue names are included (hotels, restaurants, attractions)
**Then** every venue name traces to an entity in the Vector Store via its entity ID
**And** `guardrails/entity_validator.py` validates all entity references before the proposal is finalized
**And** no venue name, price, or rating is generated by the LLM — all factual data comes from the Vector Store

### AC-4: Transport Between Venues

**Given** the itinerary includes multiple venues in a single day
**When** transport between venues is computed
**Then** each transport segment includes: method (taxi, walk, Grab, motorbike, bus), estimated time in minutes, and estimated cost
**And** transport method selection considers the Traveler Profile (e.g., mobility issues prefer taxi over walking; budget travelers prefer walking or public transport)

### AC-5: Restaurant Suggestions Respect Dietary Requirements

**Given** a Traveler Profile with dietary requirements (e.g., vegan, halal, gluten-free)
**When** restaurant suggestions are included in the itinerary
**Then** only restaurants whose Vector Store metadata indicates compatibility with the stated dietary requirements are suggested
**And** if no matching restaurants exist for a destination, the itinerary notes "limited restaurant data for dietary requirement X — verify locally" rather than suggesting unverified venues

### AC-6: Bad Weather Alternatives

**Given** an outdoor activity is included in the itinerary (e.g., beach visit, trekking, boat tour)
**When** the itinerary day is generated
**Then** a bad weather alternative is included for that time block
**And** the alternative is an indoor or weather-independent activity from the Vector Store
**And** the alternative includes the same detail level: venue name, entity ID, description, duration, cost

### AC-7: Entity Validator — Rejection of Unknown Entities

**Given** `guardrails/entity_validator.py` receives a list of entity references from the generated itinerary
**When** an entity reference cannot be found in the Vector Store (lookup by ID returns `None`)
**Then** the validator rejects that entity reference and returns a `ValidationFailure` with the missing entity details
**And** the Proposal Agent replaces the rejected entity with a verified alternative from the Vector Store
**And** if no alternative exists, the slot is marked as `"data_limited": true` with an explanation

### AC-8: Insufficient Data Handling

**Given** the Vector Store has insufficient entities for a destination (e.g., fewer than 3 attractions for a full day)
**When** the Proposal Agent attempts to generate an itinerary for that destination
**Then** the proposal indicates limited data rather than hallucinating venues
**And** the itinerary includes only verified entities with a notice: "Limited venue data available for [destination]. X of Y time blocks could not be filled with verified venues."
**And** empty slots are marked with `"data_limited": true` and a suggestion to verify locally

### AC-9: Retrieve-Then-Generate Pattern

**Given** the Proposal Agent is generating itinerary content
**When** it builds each day's activities
**Then** it follows the retrieve-then-generate pattern:
1. Query Vector Store for attractions, restaurants, and hotels in the destination/region
2. Filter results by freshness (exclude expired, warn on stale)
3. Filter restaurants by dietary compatibility
4. Pass only verified entities to the LLM for formatting and scheduling
5. The LLM arranges and describes — it does NOT invent entities
**And** all Vector Store queries flow through `VectorStoreProtocol`

### AC-10: Integration with AdvisoryState

**Given** the Proposal Agent completes itinerary generation
**When** the result is written back to `AdvisoryState`
**Then** `AdvisoryState.proposal` contains the complete itinerary data structure
**And** `AdvisoryState.stage` is updated to `"proposing"`
**And** any validation failures or data limitations are appended to `AdvisoryState.errors`
**And** if the entity validator rejects entities, the replacement attempts and outcomes are logged

### AC-11: Unit Test Coverage

**Given** the test suites at `agents/proposal/tests/` and `guardrails/tests/`
**When** tests are run with `pytest`
**Then** the following scenarios are covered:
- Itinerary generates correct number of days matching trip duration
- Each day has morning, afternoon, and evening blocks
- All entity references pass validation against mock Vector Store
- Entity validator rejects unknown entity IDs
- Entity validator triggers replacement with verified alternative
- Insufficient data produces `data_limited` markers instead of hallucinated venues
- Dietary filtering excludes incompatible restaurants
- Bad weather alternatives are included for outdoor activities
- Transport segments respect mobility constraints from profile
- Retrieve-then-generate pattern is followed (LLM receives only verified entities)
**And** all tests pass with mock `LLMServiceProtocol` and mock `VectorStoreProtocol` — no Qdrant or Ollama required

## Dev Notes

### Critical Architecture Constraints

- **GUARDRAILS STORY**: This is the story that establishes the entity validation guardrail pattern used by ALL downstream proposal features (Story 3.6, Story 3.7). `guardrails/entity_validator.py` is a reusable component, not proposal-specific.
- **Retrieve-then-generate is non-negotiable**: The LLM NEVER generates venue names, prices, or ratings. It receives pre-retrieved entities and arranges/describes them. This is NFR-1 (Zero Hallucination) enforced architecturally.
- **Protocol-based DI**: The proposal node receives `LLMServiceProtocol` and `VectorStoreProtocol` via dependency injection. Never import `OllamaLLMService` or `QdrantVectorStore` directly.
- **Pydantic BaseModel for all state**: All schemas are Pydantic, not TypedDict or dataclass (architecture decision AR-5). Note: `SearchResult` in `rag/hybrid_search.py` uses `dataclass` — proposal schemas must NOT follow that pattern; use Pydantic.
- **Errors in state, not exceptions**: If the Vector Store is unreachable or the LLM fails, append to `AdvisoryState.errors`. Never raise inside an agent node.
- **No cross-agent imports**: Read only from `AdvisoryState.traveler_profile` and `AdvisoryState.calculations`. Never import from `agents/profiling/` or `agents/calculation/`.
- **Freshness filtering**: All retrieved entities must pass through `rag/freshness.py` `filter_with_warnings()`. Expired entities are excluded. Stale entities are included with warnings attached.
- **structlog everywhere**: All logging via structlog with `session_id`, `tenant_id`, `agent_name="proposal"` in every log entry.
- **Co-located tests**: Agent tests in `agents/proposal/tests/`, guardrail tests in `guardrails/tests/`.

### Entity Validator Design

The entity validator is a guardrail component, not a proposal-specific tool. It lives in `guardrails/` because it will be reused by Story 3.6 (price validator) and any future proposal component that references Vector Store entities.

```python
# guardrails/entity_validator.py
import structlog
from app.agents.protocols import VectorStoreProtocol

logger = structlog.get_logger()


class EntityValidationResult(BaseModel):
    valid: list[dict]
    invalid: list[ValidationFailure]
    all_valid: bool


class EntityValidator:
    """Validates entity references against the Vector Store.

    This is a guardrail — it runs AFTER the LLM generates output but BEFORE
    the proposal is finalized. Any entity the LLM references must exist.
    """

    def __init__(self, vector_store: VectorStoreProtocol) -> None:
        self.vector_store = vector_store

    async def validate_entities(
        self, entity_references: list[dict], session_id: str = ""
    ) -> EntityValidationResult:
        valid = []
        invalid = []

        for ref in entity_references:
            entity_id = ref.get("entity_id", "")
            try:
                entity = await self.vector_store.get_by_id(entity_id)
                if entity is not None:
                    valid.append(ref)
                else:
                    invalid.append(ValidationFailure(
                        entity_id=entity_id,
                        entity_name=ref.get("venue_name", "unknown"),
                        reason="Entity not found in Vector Store",
                    ))
            except Exception as e:
                logger.error(
                    "guardrail.entity_validation_error",
                    entity_id=entity_id,
                    error=str(e),
                    session_id=session_id,
                )
                invalid.append(ValidationFailure(
                    entity_id=entity_id,
                    entity_name=ref.get("venue_name", "unknown"),
                    reason=f"Vector Store lookup failed: {str(e)}",
                ))

        logger.info(
            "guardrail.entity_validation_complete",
            session_id=session_id,
            total=len(entity_references),
            valid_count=len(valid),
            invalid_count=len(invalid),
        )

        return EntityValidationResult(
            valid=valid,
            invalid=invalid,
            all_valid=len(invalid) == 0,
        )

    async def find_replacement(
        self, failure: ValidationFailure, filters: dict
    ) -> dict | None:
        """Search for a replacement entity in the same region and type."""
        try:
            results = await self.vector_store.search(
                query=failure.entity_name,
                filters=filters,
                limit=1,
            )
            if results:
                replacement = results[0]
                logger.info(
                    "guardrail.entity_replaced",
                    original=failure.entity_name,
                    replacement=replacement.get("name", ""),
                )
                return replacement
        except Exception as e:
            logger.error(
                "guardrail.replacement_search_failed",
                original=failure.entity_name,
                error=str(e),
            )
        return None
```

### Retrieve-Then-Generate Execution Flow

This is the core pattern that enforces NFR-1. The LLM never generates factual content — it only arranges and describes pre-retrieved data.

```
For each day in trip_duration:
  1. RETRIEVE: Query Vector Store for attractions in day's destination
     → vector_store.search(destination, filters={"entity_type": "attraction"}, limit=10)
  2. RETRIEVE: Query Vector Store for restaurants in day's destination
     → vector_store.search(destination, filters={"entity_type": "restaurant"}, limit=10)
  3. FILTER: Apply freshness → filter_with_warnings(results)
  4. FILTER: Apply dietary requirements → match metadata_extra.dietary_tags
  5. GENERATE: Pass verified entity data to LLM with DAY_PLANNING_PROMPT
     → LLM receives JSON of real entities only, arranges into morning/afternoon/evening
  6. PARSE: Extract structured ItineraryDay from LLM response
  7. VALIDATE: Run EntityValidator on all entity_ids in the generated day
  8. REPLACE: For any invalid references, find_replacement()
  9. FALLBACK: If replacement fails, mark slot as data_limited
```

### Dietary Filtering Logic

Restaurant metadata in the Vector Store uses `metadata_extra.dietary_tags` (list of strings). Filtering logic:

```python
def filter_restaurants_by_dietary(
    restaurants: list[dict], requirements: list[str] | None
) -> list[dict]:
    """Filter restaurants by dietary compatibility.

    If no dietary requirements, return all restaurants.
    If requirements exist, return only restaurants whose dietary_tags
    include at least one matching tag.
    """
    if not requirements:
        return restaurants

    compatible = []
    for r in restaurants:
        tags = (r.get("metadata_extra") or {}).get("dietary_tags", [])
        if any(req.lower() in [t.lower() for t in tags] for req in requirements):
            compatible.append(r)
    return compatible
```

```python
        "motorbike": {"duration_range": (10, 30), "cost": 1.5},
    },
    "rural": {  # Sapa, Mekong Delta
        "taxi": {"duration_range": (20, 60), "cost": 8.0},
        "motorbike": {"duration_range": (15, 45), "cost": 2.0},
    },
}

def select_transport_method(profile: dict, destination_type: str) -> str:
    """Select transport method based on traveler profile."""
    mobility = profile.get("mobility_needs")
    travel_style = profile.get("travel_style")

    if mobility and mobility != "none":
        return "taxi"  # Accessible transport for mobility needs
    if travel_style == "luxury":
        return "taxi"
    if travel_style == "budget":
        return "walk" if destination_type == "city" else "motorbike"
    return "grab"  # Default mid-range
```

### Outdoor Activity Detection

Activities are classified as outdoor/indoor based on entity metadata or type heuristics:

```python
OUTDOOR_KEYWORDS = [
    "beach", "lake", "river", "mountain", "trek", "hike", "boat", "cruise",
    "island", "waterfall", "cave entrance", "park", "garden", "cycling",
    "kayak", "snorkel", "dive", "surf", "zipline", "motorbike tour",
]

def is_outdoor_activity(entity: dict) -> bool:
    """Determine if an activity is weather-dependent."""
    name = (entity.get("name") or "").lower()
    desc = (entity.get("description") or "").lower()
    combined = f"{name} {desc}"
    return any(keyword in combined for keyword in OUTDOOR_KEYWORDS)
```

```python
class MockVectorStore:
    """Mock Vector Store for testing entity validator and proposal agent."""

    def __init__(self, entities: list[dict] | None = None):
        self._entities = {e["id"]: e for e in (entities or [])}

    async def search(self, query: str, filters: dict, limit: int = 10) -> list[dict]:
        results = []
        for entity in self._entities.values():
            match = True
            for key, value in filters.items():
                if entity.get(key) != value:
                    match = False
                    break
            if match:
                results.append(entity)
        return results[:limit]

    async def get_by_id(self, entity_id: str) -> dict | None:
        return self._entities.get(entity_id)
```

### Data Coverage Summary Format

```
"24 of 24 time blocks filled with verified venues"        # Perfect coverage

"8 of 24 time blocks filled with verified venues"         # Low coverage — destination lacks data
```

This summary is written to `Itinerary.data_coverage_summary` and surfaced in the proposal.

### Anti-Patterns — DO NOT

- **DO NOT** let the LLM generate venue names, prices, or ratings. All factual data comes from the Vector Store. This is the defining constraint of this story.
- **DO NOT** import from `agents/profiling/` or `agents/calculation/`. Read from `AdvisoryState` only.
- **DO NOT** import `QdrantVectorStore` or `OllamaLLMService` directly. Use `VectorStoreProtocol` and `LLMServiceProtocol` only.
- **DO NOT** hallucinate venues when the Vector Store has insufficient data. Mark slots as `data_limited` with an honest explanation.
- **DO NOT** use TypedDict or dataclass for schemas. Use Pydantic BaseModel everywhere.
- **DO NOT** raise exceptions inside agent nodes. Append to `AdvisoryState.errors`.
- **DO NOT** skip freshness filtering. All entities must pass through `filter_with_warnings()`.
- **DO NOT** assume dietary compatibility if `metadata_extra.dietary_tags` is missing. Treat absent tags as incompatible when dietary requirements exist.
- **DO NOT** implement accommodation comparison table, budget breakdown, or booking actions — those are Story 3.6.
- **DO NOT** implement PDF export or shareable link — that is Story 3.7.
- **DO NOT** put entity validator tests in `agents/proposal/tests/`. They belong in `guardrails/tests/` because the validator is a shared guardrail.
- **DO NOT** create a `utils.py` file. Name files by purpose.

### Testing Strategy

All tests use `MockVectorStore` and `MockLLMService` (from `conftest.py` or local fixture). No Qdrant or Ollama dependency.

**Entity Validator Tests** (in `guardrails/tests/test_entity_validator.py`):
1. Seed `MockVectorStore` with known entities
2. Pass entity references (some valid, some with fake IDs) to `validate_entities()`
3. Assert correct categorization into `valid` and `invalid`
4. For replacement tests, verify `find_replacement()` returns a matching entity or `None`

**Proposal Agent Tests** (in `agents/proposal/tests/test_itinerary_generation.py`):
1. Create `AdvisoryState` with pre-populated `traveler_profile` and `calculations`
2. Seed `MockVectorStore` with known entities for the destination
3. Create `MockLLMService` that returns pre-formatted JSON matching the expected schema
4. Invoke `proposal_node(state, mock_llm, mock_vector_store)`
5. Assert: correct day count, block structure, entity validity, dietary filtering, transport methods, weather alternatives, data coverage summary

**Key test assertion**: Verify the LLM prompt received by `MockLLMService` contains only entity data from the mock Vector Store — confirming retrieve-then-generate pattern is followed.
