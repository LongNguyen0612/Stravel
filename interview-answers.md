## 5.1) PYTHON DEEP DIVE

### GIL la gi? No anh huong nhu the nao den performance?

**Answer (EN):**

The GIL (Global Interpreter Lock) is a mutex in CPython that allows only one thread to execute Python bytecode at a time, even on multi-core machines.

This means CPU-bound tasks do not benefit from multi-threading in Python. For example, if you run two CPU-heavy calculations in two threads, they still execute one at a time because of the GIL.

However, the GIL is released during I/O operations like network calls, file reads, or database queries. That is why multi-threading still works well for I/O-bound workloads. In SuperAnne and TravelHub, most of our work is I/O-bound (API calls, database queries, LLM requests), so we use async/await rather than threads, which avoids the GIL problem entirely.

For truly CPU-bound work, the solution is `multiprocessing`, which creates separate processes each with its own GIL. In the billing system at VCCorp, we used Celery workers (separate processes) for heavy billing calculations so they could run in parallel across CPU cores.

### Python quan ly memory nhu the nao?

**Answer (EN):**

Python uses two mechanisms: reference counting and a cyclic garbage collector.

**Reference counting:** Every object has a counter tracking how many references point to it. When the counter drops to zero, the memory is freed immediately. For example, when a variable goes out of scope or is reassigned, the old object's reference count decreases.

**Cyclic garbage collector:** Reference counting alone cannot handle circular references, for example when object A references object B and B references A. The cyclic GC periodically detects and cleans up these cycles. It uses a generational approach with three generations. Newly created objects are in generation 0, and objects that survive garbage collection are promoted to older generations, which are collected less frequently.

In practice, for SuperAnne's RAG pipeline, I was careful about memory when processing large document batches during ingestion. Loading thousands of documents into memory at once could cause issues, so we used generators and streaming to process chunks incrementally rather than holding everything in memory.

### `__slots__` la gi va khi nao dung?

**Answer (EN):**

By default, Python objects store their attributes in a `__dict__` dictionary, which is flexible but uses more memory. `__slots__` tells Python to allocate a fixed set of attributes, skipping the `__dict__` entirely.

```python
class Embedding:
    __slots__ = ['vector', 'doc_id', 'metadata']
    def __init__(self, vector, doc_id, metadata):
        self.vector = vector
        self.doc_id = doc_id
        self.metadata = metadata
```

This reduces memory usage per instance by roughly 40-50% and slightly improves attribute access speed. I would use this when creating millions of small objects, for example, in the billing system at VCCorp, we processed millions of metering events where each event was a lightweight object. Using `__slots__` reduced memory consumption significantly.

The trade-off is you cannot add new attributes dynamically, so it is best for data-heavy objects with a known fixed structure.

### Generator va Iterator khac nhau nhu the nao?

**Answer (EN):**

An **iterator** is any object that implements `__iter__()` and `__next__()`. A **generator** is a simpler way to create iterators using the `yield` keyword.

The key advantage is **lazy evaluation**: generators produce values one at a time instead of loading everything into memory.

```python
# Instead of loading all documents into memory
def load_all_documents(paths):
    return [read_document(p) for p in paths]  # All in memory at once

# Generator yields one at a time
def load_documents(paths):
    for p in paths:
        yield read_document(p)  # One at a time, memory efficient
```

In SuperAnne's RAG ingestion pipeline, I used generators extensively. When processing hundreds of financial documents for chunking and embedding, loading all documents at once would consume too much memory. Instead, the pipeline streams documents through a generator chain: read -> chunk -> embed -> store, processing one document at a time.

In the billing system, generators were used to stream millions of Kafka events through the processing pipeline without buffering them all in memory.

### Context Manager la gi? Khi nao dung?

**Answer (EN):**

A context manager handles setup and teardown logic automatically using the `with` statement. It ensures resources are properly cleaned up even if an exception occurs.

```python
# Built-in example
with open('file.txt') as f:
    data = f.read()
# File is automatically closed, even if an exception occurs

# Custom context manager
from contextlib import contextmanager

@contextmanager
def db_transaction(session):
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()
```

In SuperAnne, I used custom context managers for database transaction management, ensuring that if any step in a RAG ingestion batch fails, the transaction rolls back cleanly. In TravelHub, context managers managed supplier API connections, ensuring connections are properly released back to the pool even when supplier APIs time out or return errors.

### Metaclass la gi?

**Answer (EN):**

A metaclass is the "class of a class." Just as a class defines how instances behave, a metaclass defines how classes behave. The default metaclass is `type`.

```python
class SingletonMeta(type):
    _instances = {}
    def __call__(cls, *args, **kwargs):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]

class DatabaseConnection(metaclass=SingletonMeta):
    pass
```

In practice, metaclasses are rarely needed. I have used them in limited cases, for example, creating a registry pattern where all subclasses of a base class are automatically registered when defined. In the billing system at VCCorp, we had a plugin-like architecture for different billing calculators, and a metaclass automatically registered each new calculator class.

However, for most use cases, decorators, `__init_subclass__`, or class factories are simpler alternatives. I prefer the simplest tool that solves the problem.

### Descriptor la gi?

**Answer (EN):**

A descriptor is any object that implements `__get__`, `__set__`, or `__delete__`. They control how attribute access works on a class. Python's `property`, `classmethod`, and `staticmethod` are all built on descriptors.

```python
class ValidatedField:
    def __init__(self, min_val, max_val):
        self.min_val = min_val
        self.max_val = max_val

    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, obj, objtype=None):
        return getattr(obj, f'_{self.name}', None)

    def __set__(self, obj, value):
        if not self.min_val <= value <= self.max_val:
            raise ValueError(f'{self.name} must be between {self.min_val} and {self.max_val}')
        setattr(obj, f'_{self.name}', value)

class FinancialInput:
    age = ValidatedField(18, 100)
    risk_score = ValidatedField(1, 10)
```

This pattern is useful for reusable validation logic. In SuperAnne, a similar approach could validate financial inputs like age ranges, income brackets, or risk scores consistently across different workflow steps without repeating validation code.

### `__new__` va `__init__` khac nhau nhu the nao?

**Answer (EN):**

`__new__` creates the instance (allocates memory), while `__init__` initializes it (sets attributes).

```python
class Immutable:
    def __new__(cls, value):
        instance = super().__new__(cls)
        instance._value = value  # Set before __init__
        return instance

    def __init__(self, value):
        pass  # Cannot modify _value here in a truly immutable design
```

`__new__` is called first and returns the new object. `__init__` receives that object and sets it up. Most of the time you only need `__init__`. `__new__` is used for special cases like:

- **Singleton pattern:** Return an existing instance instead of creating a new one.
- **Immutable types:** When subclassing `str`, `int`, or `tuple`, you must use `__new__` because the value is set at creation time.
- **Custom object caching:** Return a cached instance for the same arguments.

### Python typing nang cao: Generic, Protocol, TypeVar?

**Answer (EN):**

Advanced typing makes Python code more maintainable and IDE-friendly without sacrificing flexibility.

**TypeVar** defines a generic type variable:

```python
from typing import TypeVar, Generic

T = TypeVar('T')

class Repository(Generic[T]):
    def get(self, id: str) -> T: ...
    def save(self, entity: T) -> None: ...

class BookingRepository(Repository['Booking']):
    def get(self, id: str) -> Booking: ...
```

In TravelHub, I used generics for the repository pattern so that each entity type (Booking, Supplier, Client) had its own typed repository with correct return types.

**Protocol** defines structural typing (duck typing with type safety):

```python
from typing import Protocol

class SupplierAdapter(Protocol):
    def search(self, query: SearchQuery) -> list[SearchResult]: ...
    def book(self, request: BookingRequest) -> BookingResult: ...

# Any class implementing these methods satisfies the protocol
# No inheritance required
class HotelSupplierA:
    def search(self, query: SearchQuery) -> list[SearchResult]: ...
    def book(self, request: BookingRequest) -> BookingResult: ...
```

In TravelHub, I used Protocol to define the supplier adapter interface. Each supplier (hotel, flight, car rental) implements the same protocol, but without forcing inheritance. This keeps supplier implementations decoupled and testable.

### Concurrency trong Python: threading, multiprocessing, asyncio?

**Answer (EN):**

Python offers three concurrency models, each suited for different workloads:

| Model | Best for | GIL impact | Example |
|-------|----------|------------|---------|
| `threading` | I/O-bound with blocking libs | Released during I/O | Legacy DB drivers |
| `multiprocessing` | CPU-bound | Separate GIL per process | Billing calculations |
| `asyncio` | I/O-bound at scale | Single thread, no GIL issue | API calls, DB queries |

In my projects:

- **asyncio** (SuperAnne, TravelHub): Primary choice. FastAPI is async-native. We fan out multiple supplier API calls or LLM requests concurrently with `asyncio.gather()`. One event loop handles thousands of concurrent I/O operations efficiently.

- **multiprocessing** via Celery (VCCorp Billing): For CPU-intensive billing calculations like processing millions of metering events, aggregating costs, and generating invoices. Each Celery worker is a separate process with its own GIL.

- **threading**: Rarely used directly. Most libraries we use (httpx, asyncpg, aiobotocore) support async natively. Threading is only needed when a library is synchronous and blocking, for example wrapping a legacy SDK that does not support async.

The key decision: if your bottleneck is waiting for external services (network I/O), use asyncio. If your bottleneck is CPU computation, use multiprocessing.

## 8) PGVECTOR (DEEP)

### Ban dung pgvector nhu the nao?

**Answer (EN):**

In SuperAnne, pgvector is used as the vector store within Aurora PostgreSQL to enable similarity search for our RAG pipeline.

Financial documents such as policies, advisory guidelines, and regulatory documents are chunked, embedded, and stored as vectors. When a user submits a query, it is converted into an embedding and matched against stored vectors using cosine similarity. The top-k most relevant chunks are retrieved and passed as context to the LLM via AWS Bedrock for generation.

The key advantage is that embeddings live alongside structured data in the same PostgreSQL database, so we can combine vector similarity search with SQL filters in a single query.

### Vi sao chon pgvector?

**Answer (EN):**

Three main reasons.

First, it integrates natively with PostgreSQL, which we were already using (Aurora PostgreSQL). This means no additional infrastructure to manage, and the operations team only needs to maintain one database system.

Second, it allows combining vector search with structured SQL filters in a single query. For example, we can filter documents by type, category, or effective date before performing vector similarity search. This is much harder with standalone vector databases.

Third, Aurora PostgreSQL provides built-in high availability, automated backups, and seamless scaling, which are critical for a production fintech system.

### Optimize pgvector nhu the nao?

**Answer (EN):**

Several optimization strategies.

First, apply metadata filters before vector search. For example, filtering by document type or category first narrows the search space, which improves both speed and relevance.

Second, create appropriate indexes. We use IVFFlat or HNSW indexes on the embedding column to accelerate similarity search at scale.

Third, tune the top-k parameter. Retrieving too many results adds noise, while too few may miss relevant context. We experimented to find the optimal balance for our use case.

Fourth, optimize chunk size and overlap during ingestion to ensure each chunk is semantically meaningful and self-contained.

### Kho khan lon nhat la gi?

**Answer (EN):**

The biggest challenge was handling different supplier data formats.

### Token luu o dau?

**Answer (EN):**

I prefer HTTP-only cookies for storing authentication tokens in production systems.

HTTP-only cookies cannot be accessed by JavaScript, which means they are not vulnerable to XSS attacks. In TravelHub, since we handle B2B client sessions and sensitive booking data, security is critical. The token is set as an HTTP-only, secure, SameSite cookie by the backend, and the browser automatically sends it with every API request.

Storing tokens in localStorage exposes them to any JavaScript running on the page, including malicious scripts injected via XSS vulnerabilities. For a B2B platform handling financial transactions like booking payments, this risk is not acceptable.

### Khi nao dung localStorage?

**Answer (EN):**

localStorage is appropriate for non-sensitive, user-preference data.

For example, in TravelHub, we use localStorage to persist UI preferences such as selected filters, display settings, sorting preferences, or language selection. This improves user experience because these preferences survive page refreshes without requiring an API call. The key rule is: never store tokens, credentials, or any sensitive information in localStorage.

### Auth flow nhu the nao?

**Answer (EN):**

TravelHub uses token-based authentication for B2B clients.

The flow works as follows: a client authenticates with their credentials, the backend validates them against PostgreSQL and issues a JWT token. This token is stored in an HTTP-only cookie and automatically attached to subsequent API requests. The FastAPI backend validates the token on every request, checks permissions, and either processes the request or returns a 401/403 error.

For API-to-API integrations (since TravelHub is a B2B middleware), we also support API key-based authentication for downstream clients that consume our standardized booking APIs programmatically.

### Bao mat nhu the nao?

**Answer (EN):**

Security in TravelHub focuses on several layers.

First, preventing XSS by using HTTP-only cookies for tokens, sanitizing all user inputs, and using React's built-in escaping for rendered content.

Second, protecting data in transit with HTTPS everywhere and encrypting sensitive data at rest in PostgreSQL.

Third, validating all inputs on the backend using FastAPI's Pydantic models, which prevents injection attacks and ensures data integrity.

Fourth, implementing proper CORS policies to restrict which domains can make API requests.

Fifth, rate limiting on search and booking APIs to prevent abuse, since we are calling external supplier APIs that may have their own rate limits.

### Dong bo nhieu tab nhu the nao?

**Answer (EN):**

We use the `storage` event on localStorage for cross-tab synchronization.

For example, when a user logs out in one tab, we write a logout signal to localStorage. Other open tabs listen for the `storage` event and immediately clear the session and redirect to the login page. This prevents a situation where a user logs out in one tab but remains logged in on another tab, which could be a security risk.

We also use this pattern for syncing booking cart updates across tabs, so if a user adds a service in one tab, it reflects in other open tabs.

## 13) CUSTOM SDK - TRAVELHUB

### You mentioned TravelHub is a B2B middleware. Did you build a client SDK? How did you design it?

**Answer (EN):**

Yes. Since TravelHub aggregates multiple travel suppliers into a unified booking lifecycle, our B2B clients need to integrate with our APIs programmatically. I built a Python SDK so clients can integrate in hours instead of days, rather than each writing their own HTTP code with inconsistent authentication, error handling, and retries.

The SDK is async-first using `httpx.AsyncClient`, with a synchronous wrapper for clients that do not use async. It is organized around the booking lifecycle: `client.search()`, `client.booking.create()`, `client.booking.cancel()`, `client.booking.amend()`. All request and response objects use Pydantic models mirroring our backend data contracts, so clients get type safety, IDE auto-completion, and runtime validation out of the box.

For error handling, I defined custom exceptions like `SupplierTimeoutError` and `RateLimitError`, each carrying the HTTP status code, API error message, and a request ID for debugging. The SDK also includes built-in retry with exponential backoff for transient failures, which is important because our backend calls external supplier APIs that can be unreliable.

We distributed it via a private PyPI registry with semantic versioning, so clients can pin versions and upgrade at their own pace. The key design principle was keeping the SDK thin: it handles transport concerns like auth, retries, serialization, and error mapping, but contains no business logic. Business logic stays server-side so all clients benefit from updates without upgrading the SDK.
